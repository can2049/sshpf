# sshpf 设计说明

本文记录关键设计决策与其依据。所有结论都有实测支撑，证据在
`docs/research/pure-rust-ssh-plan.md`（纯 Rust 化决策）、
`docs/research/pure-rust-ssh-spike.md`（三种转发端到端验证）、
`docs/research/pure-rust-ssh-russh.md`（russh API 核实）、
`docs/research/pure-rust-ssh-config.md`（config/密钥/agent 生态）、
以及更早的 `docs/research/tech-options.md`、`docs/research/prior-art.md`。

## 1. 为什么用 russh 而不是调用系统 ssh

v1 曾经用 `std::process::Command` 调系统 `ssh`，理由是「ProxyJump / IdentityFile /
ssh-agent / known_hosts 的语义太复杂，重写容易漏」。这个判断在当时成立，但代价是
**Linux 和 Windows 行为不一致**（Windows 上要用户自装 OpenSSH），而且失败原因只能
靠正则解析 stderr 文本。

换成 `russh` 后实测（`docs/research/pure-rust-ssh-spike.md`）：

| 维度 | 系统 `ssh` 子进程（旧） | `russh`（现在） |
|---|---|---|
| 跨平台一致性 | 依赖用户装 OpenSSH | **同一套代码路径** |
| `-L` | ✓ | ✓ 本地 `TcpListener` + `direct-tcpip` |
| `-R` | ✓ | ✓ `tcpip_forward` + `forwarded-tcpip` 回调 |
| `-D` | ✓ | ✓ 自写 SOCKS5（约 150 行） |
| ProxyJump | 原生 | ✓ `connect_stream` 套 channel（实测三跳） |
| ssh-agent | 原生 | ✓ Unix socket / Windows named pipe |
| 失败原因 | stderr 正则，脆弱 | **结构化 `russh::Error`** |
| 就绪判定 | 解析 debug 日志 | **真实 bind / 协议回复** |
| 运行时依赖 | `ssh` 二进制 | **零** |
| 二进制体积 | 1.63 MB | 4.34 MB |

决定性收益不是"少一个依赖"，而是**三类实测过的误判 bug 从根上消失**（见 §3）。

## 2. `~/.ssh/config` 由 `ssh2-config` 解析

不再调用 `ssh -G`。`ssh2-config` 0.9.0 是纯 Rust、零 C 依赖（crate 名里的 "ssh2"
只是历史原因，`cargo tree` 里没有 `libssh2-sys`），覆盖 `Include`、`Host` 多模式
与通配、否定、`Host *` 继承、`ProxyJump`、`IdentityFile`。

### 必须自己兜住的一个上游 bug

`ssh2-config` 的 `Field` 枚举里**没有 `Match`**。`Match` 行走
`UnknownField` 分支被忽略，**但它后面的选项会继续写进上一个 `Host` 块**：

```text
Host web1  { HostName 10.0.0.1; User alice }
Match host foo { User ignored; Port 9999 }

ssh2-config query(web1) -> user="ignored" port=9999   ← 静默错误
ssh -G -F ...        web1 -> user=alice    port=22     ← 正确
```

静态错误比崩溃更危险：用户看到的是错误的 user/port 且没有报错。
`ssh::config::strip_match_blocks` 在解析前剔除 `Match` 块，并有单测固定这个行为。

另外两处缺口也由薄封装补上：`HostName` 未设置时回退到 alias（OpenSSH 语义），
以及 `IdentityFile` 的 `~` / `%d` 展开。

**不再需要合成配置。** 旧方案要把 `ssh -G` 的 73 个键烘焙成一次性 `-F` 文件，
并处理 `ProxyJump` 链整体烘焙、含空格值加引号等坑。纯 Rust 里我们直接把
`HostName`/`Port`/`User` 交给 `connect()`，`~/.ssh/config` 里的
`LocalForward` 也不会被带进来——因为根本不会去读它。

## 3. 就绪判定：从"猜日志"变成"看结果"

**旧实现**靠解析 ssh 的 debug 输出，有三类实测过的假信号：

1. `-L` 双栈半失败：一个地址族绑上了，另一个报错，但 `Entering interactive
   session.` 照常打印。
2. **ProxyJump 子进程的假就绪**：跳板 fork 出的子 ssh 自己也会打印
   `Entering interactive session.`，混进我们的 stderr。
3. `-R` 顺序倒置：`Entering interactive session.` **早于**真正的
   `remote forward success for`，只看前者会误判成功。

**现在**就绪是二值的、来自真实结果：

- `-L` / `-D`：`TcpListener::bind` 返回 `Ok` 才算就绪；
- `-R`：`tcpip_forward()` await 到服务端对 `GLOBAL_REQUEST` 的回复才算就绪。

`TunnelEvent::Ready` 是通往 `TunnelStatus::Up` 的**唯一**路径，`app::on_ready`
不读任何日志文本。三类假信号在结构上不可能再发生。

## 4. 生命周期：tokio task 取代子进程

旧实现要处理进程组、`PR_SET_PDEATHSIG`、Windows Job Object，因为子进程会
在父进程被杀后变成孤儿并占住端口。

现在每条隧道是**一个后台线程 + 一个 `current_thread` tokio runtime**：

- 停止 = 置停止标志 → `select!` 立刻返回 → runtime 丢弃 → socket 关闭 → 会话结束；
- 端口释放实测 **172 µs**；
- `SIGKILL` sshpf 也不会留孤儿——没有子进程，socket 由内核关闭；
- 30 次启停循环 **无 fd 泄漏**。

因此 `sys` 层从两个 200 行的平台文件缩减到只剩文件权限与信号两类函数
（`src/sys/unix.rs` 55 行 / `src/sys/windows.rs` 40 行）。

## 5. 重试策略

失败分两类：

- **配置类**（端口占用、权限、认证、主机密钥、远端拒绝）：重试无用，标
  `✗ 失败` 并停下。
- **网络类**（连接拒绝、超时、DNS、进程异常退出）：`◌ 重试`，指数退避
  2s→4s→…→30s，尊重 `auto_restart` 开关。

`arm_retry` 在启动时插入的占位记录 `attempt = 0`，`tick_retries` 只处理
`attempt >= 1` 的记录——否则占位符会让程序在启动瞬间陷入无限重连。
这是集成测试发现并修复的真实缺陷。

## 6. 配置与状态的分离

- `~/.config/sshpf/config.toml`：用户意图（转发定义、`enabled`），可手改，
  原子写（temp + rename），`0600`，目录 `0700`。
- `~/.local/state/sshpf/state.toml`：上次运行时间与每条的末次状态，纯诊断用。
  启停转发不重写用户配置之外的东西。

放 `~/.ssh/` 是错的（那是 OpenSSH 的领地，误写会破坏用户配置）；放项目目录
也是错的（TUI 是全局工具）。

## 7. 并发模型

**UI 线程保持同步。** 主线程 `crossterm::event::poll(200ms)` 阻塞等键，每帧非阻塞地：

1. `try_recv` 排空隧道线程发来的事件；
2. 处理到期的重试；
3. `terminal.draw()`。

**每条隧道一个后台线程 + 一个 `current_thread` tokio runtime**，事件通过
`std::sync::mpsc` 回灌。UI 永远不会阻塞在某个慢主机的握手或数据拷贝上。

为什么不用共享 runtime：实测 10 条隧道并发建立仅 80 ms（单条约 8 ms 摊薄），
本项目规模（几条到几十条）下"一线程一 runtime"完全够用，且隔离性更好——
一条隧道 panic 不影响其它隧道。

`russh::client::Handle` **不是 `Clone`**，所以单条隧道内的多个 task 共享它必须
用 `Arc<Handle>`。

## 8. 主机选择：内嵌下拉框而非独立弹窗

新增转发时最常做的第一件事是选一台主机，所以「从 `~/.ssh/config` 选主机」必须是
**看得见的入口**，不能藏在快捷键后面。

v1 初版是 `ctrl+h` 打开一个居中模态框，实际使用中很难被发现。改成：

- **SSH 主机字段本身就是下拉框**，右侧有 `▾`（展开时 `▴`），空值时显示
  `(N台可选)`，让用户一眼看到有列表可挑。
- 展开后在**表单内部**紧贴该字段下方渲染列表，不另开模态窗口，上下文不丢。
- `enter`（或 `F2` / `ctrl+h`）展开（不是在主机字段上直接提交表单），`esc` 收起不改值，
  `tab` 切字段时自动收起。
- 输入即过滤；别名优先匹配，别名无命中时才回退到 `user@host:port` 匹配——
  否则输入 `de` 会因为某台机器的用户名是 `deploy` 而列出 `bastion-prod`，
  看起来像 bug。
- 选中后填别名，名称留空时同步填别名；**字段一旦有值就不再显示 `(N台可选)`**，
  否则选中的主机名会被提示挤出去，用户无法确认自己选了什么。

实现上是个 8 行的滚动窗口（`HOST_DROPDOWN_ROWS`），键处理与渲染共用同一个常量，
避免两边算出的可见行数不一致。

## 9. 表单两阶段编辑与本地端口推荐

### 两阶段编辑

方向键在表单里是最常按的键。如果按一下就改动值，用户只是想把光标挪到下一个
字段却会改变类型或勾选状态，很挫败。所以表单区分两种模式：

- `EditMode::Navigating`（默认）：`↑↓`/`tab` 只移动高亮
- `EditMode::Editing`：在文本字段上按 `enter` 才进入，此时才接收输入；
  `enter`/`esc` 退出编辑，`tab` 退出并前进

视觉上用三档区分，避免用户不知道自己处在哪种状态：编辑态是**实心选中条**，
仅高亮是**加粗强调色**，其余是普通色。光标只在编辑态出现。

枚举/开关类字段（类型、自动重连）不需要进入编辑态，`enter`/`←`/`→`/空格直接操作。

### 本地端口推荐

填远端端口后自动推导本地端口，但**只是建议**，用户始终可以改。规则：

1. 远端端口 ≥1024 且空闲 → 用同一数值（最符合直觉）
2. 远端端口 <1024 → 用 `remote + 2200` 的惯用别名（`22 → 2222`）。
   这里有个实测踩到的坑：低位端口绑定需要 root，`port_available` 会把
   **所有** <1024 端口都报告为不可用，若照搬「从远端端口开始向上扫」，
   扫描预算会在特权区间里全部耗尽，最后只能报「找不到可用端口」。
3. 端口被系统占用 → 向上顺延
4. 端口被其它转发条目占用 → 跳过。这一条不能只靠 OS 探测：
   已停用的转发并不在监听，但它一旦启动就会冲突。
5. 用户手改过本地端口 → `local_port_auto = false`，之后不再自动覆盖
6. 编辑既有转发 → 同样不自动推导，保留原值

### 字段顺序

顺序改为 `SSH 主机 → 名称 → 类型 → 远端地址 → 远端端口 → 本地地址 → 本地端口 → 自动重连`。
理由：远端是用户知道的目标（「我要访问 8080」），本地是派生出来的落地端口，
所以远端排在本地之前，填完远端就能立刻看到推荐值。

## 10. 风险操作确认

### 什么需要确认

判断标准是三条，命中任意一条就要拦：

1. **会丢数据** —— 删除条目、放弃未保存的表单输入
2. **会断连接** —— 停用、重启、批量停用、保存编辑（编辑会重建进程）
3. **事后不易察觉** —— 批量启用会一次开出很多监听端口

反过来，可逆且无副作用的操作**刻意不拦**：移动光标、过滤、看详情、启动一条
未启用的转发、新建条目。给这些加确认会让高频操作变烦，而用户一旦习惯无脑按
`y`，真正的危险确认就失效了 —— 这是确认框设计里最容易犯的错。

### 实现

`ConfirmAction` 枚举穷举所有受保护操作，`App::ask_confirm()` 统一生成提示文案。
把「哪些操作受保护」收敛到一个枚举里，好处是新增操作时编译器会强制你想清楚它
属于哪一类，而不是散落在十几个按键分支里各写一遍。

表单保存拆成两步，这是本次改动最关键的一点：

- `validated_form_config()` —— 只校验，不落盘
- `commit_form_create()` —— 新建，直接保存（增量操作）
- `commit_form_edit()` —— 编辑，**等确认后**才停进程、写配置

待保存的配置暂存在 `App.pending_form` 里，所以用户确认前运行中的进程不会被打断。
如果先停进程再弹窗，取消就会莫名其妙地把用户的连接断掉。

### 提示文案

提示由 `ask_confirm` 按 action 与当前状态生成，能带上具体上下文：

- 单条操作带条目名（`确认停用「db-prod」？`）
- 批量操作带数量（`确认停用全部 2 条运行中的转发？`）
- 退出带运行中数量，没有在跑时不提「停止」

对话框高度按文案宽度自适应（提示可能折行），避免出现大片空白。

## 11. 测试策略

### 为什么把按键分发搬出 main.rs

`main.rs` 原本承载了约 530 行按键处理（每个 overlay 一个 handler）。二进制
crate 里的私有函数无法被 `tests/` 下的集成测试调用，只能靠 pty 驱动真实 TUI
来验证 —— 慢、脆、且抓不到具体分支。

现在这些 handler 在 `src/keys.rs`（lib 内），签名统一是
`fn(app: &mut App, key: KeyEvent)`，本身无副作用，于是可以像纯函数一样测：
构造 `App`（`App::new` 不 spawn 任何进程）、喂一个 `KeyEvent`、断言 `App` 状态。
`main.rs` 只剩终端生命周期与事件循环。

### 覆盖重点

优先测「错了会静默出问题」的地方，而不是追求行覆盖率：

- **时序类**：退出事件与最后几行日志可能乱序，因此失败原因随
  `TunnelEvent::Exited` 一起传递。测试直接调 `on_exit` / `on_line` 验证迁移。
- **判定类**：`TunnelStatus::Up` 只能经由 `TunnelEvent::Ready` 到达
  （`on_ready`），任何日志文本都不得改变状态。这是最容易被"优化"掉的约束。
- **门控类**：确认框必须在动作之前弹出，且确认前不得产生任何副作用。
  表驱动穷举 6 类风险操作，逐项断言。
- **边界类**：1×1 终端、4000 字符的行、CJK 宽度、空配置、损坏的状态文件、
  越界的选中索引。这些在真实使用中一定会遇到，且往往直接 panic。

### 变异测试验证有效性

补齐测试后，故意改坏关键逻辑，确认测试会变红。以下变异全部被捕获：

| 变异 | 捕获它的测试 |
|---|---|
| 交换 `-R` 的 forward_spec 参数顺序 | `forward_spec_for_each_kind` |
| 配置权限从 0600 改成 0644（两处都改） | `save_is_0600` |
| 就绪改由日志文本触发而非 `Ready` 事件 | `happy_path_starting_to_up_is_driven_by_the_driver` |
| 停用不弹确认直接执行 | `all_risky_operations_ask_first` + `space_stops_only_after_confirmation` |
| 删除不弹确认直接执行 | 4 个测试同时失败 |
| 让 `clamp_selection` 失效 | `selection_survives_a_filter_that_shrinks_the_list` |

变异测试也纠正了一个误解：早期一次"变异存活"其实是我的 `sed` 没匹配上，
用 Python 精确替换后才真正生效。**验证测试本身有效，比增加测试数量更重要。**

### 补测过程中发现的真实缺陷

1. **表单导航态按 `esc` 静默丢失输入** —— 上一轮加确认时只改了编辑态分支，
   导航态仍直接 `close_overlay()`。这个分支恰好是用户按一次 `esc` 就会走到的。
2. **过滤后 `selected` 越界** —— 收窄过滤条件后索引可能指向不存在的行，
   而 `select_next` 只在"未越界"时前进，导致选中行消失、操作落空。
   修法是加 `clamp_selection()` 并在移动前先夹紧。

## 12. Windows 支持

### 纯 Rust SSH 让平台差异几乎消失

v1（系统 `ssh` 子进程）时 Windows 需要一整套等价机制：Job Object 替代进程组、
`KILL_ON_JOB_CLOSE` 替代 `PR_SET_PDEATHSIG`，两个平台文件各 200 行。

改用 `russh` 后**子进程不存在了**，进程树回收问题自然消失。`sys` 层剩下的差异只有：

| 关注点 | Unix | Windows |
|---|---|---|
| 文件私密性 | `chmod 0600/0700` | 用户配置文件 ACL 继承（无需操作）|
| 退出信号 | `SIGINT`/`SIGTERM`/`SIGHUP` | Ctrl-C 映射的 `SIGINT`/`SIGTERM` |

两个平台文件合计不到 100 行，且 **SSH 相关代码零平台分支**——这正是
"跨平台可靠一致性"的实质收益。

### 三个 Windows 专属的实测结论

1. **`ring` 加密后端是必须的。** `russh` 默认的 `aws-lc-rs` 在 Windows x86-64
   构建时需要 NASM 和 CMake。同一句 `cargo check --target x86_64-pc-windows-gnu`
   的对比实验里，`aws-lc` 请求了 `59×gcc / 2×NASM / 3×CMake`，
   `ring` 只请求 `9×gcc`。所以 `Cargo.toml` 显式写
   `default-features = false, features = ["ring", "flate2", "rsa"]`。
   CI 的 `windows-latest` 预装 MSVC，因此无需额外安装步骤。
   注意这是**构建期**依赖，产物仍自包含。

2. **不再需要假 ssh 夹具。** v1 曾用 `rustc` 编译一个假 ssh 可执行文件
   （因为 `/bin/sh` 脚本在 Windows 上无法执行，`os error 193`）。
   现在测试直接对着真实 SSH 协议跑，夹具问题整体消失。

3. **本地端口反查进程仅 Linux 可用**，Windows 上返回空——不影响转发本身。

### 分支保护

`main` 开启了保护，合并必须满足：

* 4 个 CI 检查全绿（`strict: true`，即分支落后也要先 rebase）
* 禁止强推、禁止删除分支
* `enforce_admins: true` —— 管理员也不能绕过
* 必需 review 批准为 0（单人仓库无法自我批准；实测 `mergeStateStatus`
  会因此卡在 `BLOCKED`）

实测验证过：CI 失败时 `gh pr merge` 被拒绝。

## 13. 从 `~/.ssh/config` 导入转发

配置里已经写着"哪台机器要转发哪个端口"，用户却要在表单里重打一遍。这个特性读
`LocalForward` / `RemoteForward` / `DynamicForward`，把它们作为表格列出、默认全勾，
取消不要的再保存。主机一旦从下拉里被接受，面板就**自己展开**——"默认全勾"若还要再按一次键
才看得见，那它只是一份藏起来的提议，不是默认。细节见 [import-forwards.md](import-forwards.md)，
本节只记决策与依据。

### 为什么不用 `ssh2-config` 的现成字段

`ssh2-config` 0.9.0 三个指令支持不对等，实测（`ALLOW_UNSUPPORTED_FIELDS`）：

| 指令 | 解析结果 | 后果 |
|---|---|---|
| `RemoteForward` | `HostParams::remote_forward: Vec<RemoteForward>`，逐条追加 | 可用 |
| `LocalForward` | 进 `unsupported_fields` | 每个指令名一条，**后覆盖前** |
| `DynamicForward` | 进 `unsupported_fields` | 同上 |

`unsupported_fields` 是 `HashMap<String, Vec<String>>`——以**指令名**为 key。同一 `Host`
写两条 `LocalForward`，只有最后一条留下：

```text
Host cloud_pc
  LocalForward 18789 127.0.0.1:18789
  LocalForward 8090 127.0.0.1:8080
  DynamicForward 1080

unsupported_fields = {"localforward": ["8090", "127.0.0.1:8080"],
                      "dynamicforward": ["1080"]}
```

`18789` 静默消失，且 `HashMap` 不保序。所以 `src/ssh/forwards.rs` 自己按行扫这三组指令；
`ssh2-config` 继续只负责连接参数（§2 的上游 `Match` bug 与这里无关，两条路径独立）。

### 作用域按 OpenSSH 语义累积

要点是**多个 `Host` 块都命中时全部累积**，不是"第一个命中就停"。`Host web` 与 `Host *`
同时贡献转发。其余规则：否定子句 `!prod` 排除整块、通配 `*`/`?` 大小写不敏感、
首个 `Host` 行之前的指令视为全局。

`Match` 块**一行都不导入**。理由不是"实现麻烦"，而是 `Match` 的转发带有连接上下文前置条件；
把它当成无条件生效，等于在用户明确设了闸的地方静默开监听端口。少导入是可接受的，
误导入不是。

### 去重按字面 key，不按语义

`SshForward::key()` = 类型 + 监听地址 + 监听端口 + 目标地址 + 目标端口（`-D` 只看前两项）。
所以 `Host *` 重复声明具体块的转发时，只留第一行——否则两条隧道抢同一端口，第二条必然
`Address already in use`。

**刻意不做地址归一化**：省略监听地址（`LocalForward 8080 …`）与 `127.0.0.1:8080` 是两个 key。
省略监听地址在 OpenSSH 里的实际含义依赖 `GatewayPorts`，`sshpf` 不替用户猜。代价是两条语义
重叠的隧道会被创建，但第二条的本地端口会被顺延（见下），不会出现失败。

### 自动展开：判定条件是「有可导入的行」

面板在主机确定的那一刻自动展开，不需要 `space`。这不是交互上的顺手，而是"默认全勾"
这个承诺能否成立的前提：一个要按键才出现的预设，对不知道入口的用户等于不存在，而特性能不能
省下重打端口的功夫，恰恰取决于这类用户。

判定只有一条规则，落在 `install_import_rows`：

```text
importable_count() > 0  → import_open = true   （可导入行已由 ImportTable::new 全部勾好）
importable_count() == 0 → import_open = false
```

用**可导入行数**而不是行数，是因为"表里有行"不等于"有可做的事"。一台主机只声明了
Unix socket 转发时，表里全是变暗的 `[–]`：自动弹出这个面板只会盖住表单，还会让
"没有可导入项"看起来像"有一堆东西等你处理"。此时面板保持关闭，但 `space`/`i` 仍能打开它——
用途从"给你默认"变为"给你解释"，因为那几行 `⚠` 原因都在。

一台主机**一条转发都没有**是另一回事：表是空的，展开也没有任何内容可解释，所以 `space`/`i`
不展开面板，而是在状态行说明「该主机在 ~/.ssh/config 中没有端口转发配置」。空面板和
"解释了为什么空"是两种信息，前者不如后者，而后者不需要一整块屏幕。

把决定"要不要展开"的逻辑从发现流程里拆出来（`refresh_import_table` 负责读配置、
`install_import_rows` 负责安装并决定可见性），是为了让这条规则可以脱离真实
`~/.ssh/config` 单测：喂一批行，断言 `import_open` 与勾选数即可。发现本身涉及文件系统，
不该成为交互规则的测试前置条件。

另外两条配套约束：

- **主机字段为空时不扫描**。`Host *` 匹配空串，扫一遍会把所有全局转发放到用户并未选择的
  别名下面，`ctrl+s` 会真的照这些行建隧道。空串是"还没选主机"，不是"匹配所有主机"。
- **同一主机重复刷新是 no-op**。`refresh_import_table` 在别名与上次相同时直接返回；否则接受
  同一台主机两次会把用户已取消的勾选打回全勾、把手动收起的面板弹回来——默认值只应生效一次，
  不该变成反复覆盖用户决定的行为。换到另一台主机则是另一份默认，于是重新展开。

主机别名的输入路径只有一条：`SSH HOST` 字段虽然算文本字段，但 `activate_field` 对它调的是
`open_host_picker()` 而不是 `begin_edit()`，导航态也没有任何分支把它写进编辑态——也就是说
这个字段在 UI 上永远进不了"正在输入"的阶段，别名的唯一来源是 `~/.ssh/config` 下拉里被接受的那一项。
`picker_accept` 写入别名后紧接着调用 `refresh_import_for_current_host()`，所以"确定主机"这个
时刻只有一个来源，不存在"打完字还没按回车"这种中间态需要额外处理。这也是为什么自动展开不需要
防抖或延迟：发现不是跟着每一下按键跑的，而是跟着一次明确的接受动作跑的。

### 不可导入的行必须列出

Unix socket 形式、`-R` 无目标，都无法表达成 `TunnelConfig`。它们**照常出现在表里**，
勾选框显示 `[–]`、整行变暗，并用原因文案替换最后一个数据列（`⚠ 端口无法解析` /
`⚠ 目标地址无法解析`）。默默隐藏会让用户以为工具漏读了配置。这些行在模型层就勾不上：
`toggle_cursor` / `check_all_visible` / `invert_visible` 都先查 `importable()`。

### 默认全选是意图，不是监听

勾选只存在内存里，不写盘、不 bind、不建线程。隧道在 `ctrl+s` 确认之后才创建。
这一条必须成立，否则"默认全选"就是"打开表单就替你开一堆端口"。
编辑已有隧道时导入面板不存在——把编辑悄悄变成批量新建是数据丢失级的问题。

### 面板在屏幕上时才接管提交

判定条件是 `!is_modifying() && import_open && !import.is_empty()`——**面板可见**，而不是
「表单里有一张非空的导入表」。后一个判据曾经是对的，因为那时面板要手动 `space` 才出现，
"有行"确实等于"用户正在用它"；面板改成默认展开之后，这个等式断了。用户完全可能故意按
`i`/`esc` 收起面板、想在表单里手填一条单条转发——若仍按"有行"走批量，`ctrl+s` 只会报
「没有勾选任何转发」，那条手填的隧道永远建不出来。收起面板于是等于"这个表单废了"。

| 面板 | `ctrl+s` | 表单字段 |
|---|---|---|
| 在屏幕上（默认） | 批量；每条勾选行一条隧道 | 忽略，只是草稿 |
| 用户主动收起 | 单条；按手填字段建一条 | 校验并采用 |

原则一句话：**校验必须对着用户正在看的那份界面**——看得见面板就校验面板，收起面板就校验表单。

原先那条实测教训仍然成立并被这条规则保住：面板在屏幕上时，把行全部取消勾选再 `ctrl+s`，
报的是「没有勾选任何转发」，而不是「名称不能为空 / 本地端口必须是 1-65535 的数字」——
后者描述的是用户从头到尾没看过、也不打算填的字段，用户以为只是取消了勾选，得到的却是
关于另一个表单的错误。

### 批量创建：先校验完再写

N 个勾选行 = N 条隧道（`TunnelConfig` 只描述一条转发）。保存路径是**整批先校验、全过才写**：

1. 逐行 `config_from_forward` + `validate_tunnel`；
2. 监听地址冲突查两遍——已保存的隧道、以及**本批次里前面的行**；
3. 任一条报错 → 错误写进表单，一条都不创建。

顺序很关键。先生成再逐条写入，会在"第 4 条校验失败"时留下 3 条用户没要求过的隧道。

`-R` 的两端要**对调**：指令里 `7000 localhost:22`，`7000` 是服务端监听、`localhost:22` 是本地目标；
而 `TunnelConfig` 的 `local_*` 恒指本机侧。填反了会静默转发错误的端口。

`-L`/`-D` 的本地端口会顺延避让：从导入的端口开始 `+1` 扫描，跳过"被其它隧道占用"
（含**未运行**的——它一旦启动就冲突）和"当前不可 bind"的。`taken` 在批次内逐条增长，
所以同批次两行要同一端口时第二行自动错开。

## 14. 逐列筛选与撤销

导入表四列（类型 / 监听 / 目标 / 原始指令）各有独立筛选，多个筛选 **AND** 到一起。

### 子串，而非主表的模糊匹配

主表 `/` 过滤用 `fuzzy_match`（needle 的字符按序出现即命中，中间可隔任意字符）。
列筛选**刻意**用大小写不敏感子串：

| 匹配器 | `1080` 会命中 |
|---|---|
| 模糊子序列 | `127.0.0.1:1080`、`127.0.0.1:10800`、`1:0:8:0`… |
| 子串（采用） | 只命中字面连续的 `1080` |

筛选端口列的目的是**精确定位一行**；返回一堆无关行等于没筛。列筛选是"缩小范围"工具
（`8080`、`localhost`、`-R`），子串才符合这个用途。主表的模糊匹配用于按名字找隧道，
语境不同，不加区分地复用是错的。

### 撤销用快照栈

每次改筛选**之前**压一份完整 `[String; 4]` 快照（上限 64，丢最旧）。
所以输入 `8080` 会压 4 份，`z` 逐字符回退；`ctrl+r` 清空四列只压 1 份，一次 `z` 全恢复。

快照式而非"记录单次编辑"的原因：筛选状态是 4 个字符串的向量，快照是最小且不会算错的实现；
增量式要处理"改哪一列、从什么改成什么"，撤销 `ctrl+r` 这种跨列操作时得记多条。64 份快照
的内存代价可以忽略（4 个短字符串）。

`undo_filter()` 返回 `bool`，空栈时提示「没有可撤销的筛选」——静默无反应会被当成按键失效。

### `f` 在筛选输入之上

`f` 用于循环切换"正在筛选哪一列"，而它的助记位置又正好在被筛选的文本输入里。实现上
`f` **优先于**筛选输入被处理：连按 `f` 会 `类型 → 监听 → 目标 → 原始指令 → 类型` 循环，
而不是第一个 `f` 打开输入、第二个 `f` 被当成字符写进筛选。

代价是**字面字符 `f` 无法输入到筛选里**。这是刻意接受的：四列内容分别是端口、主机地址和
指令名（`LocalForward` 等），没有哪一列需要匹配字母 `f`；`←`/`→` 也能换列，退格能改错。
反过来，如果让 `f` 被输入吃掉，底部的「f/←→ 选列」提示就成了谎话——按第二次时行为突然改变，
是那种"看起来能用、用起来出错"的设计。

### 面板打开时键位归面板——但编辑态例外

面板展开时，`↑↓`/`j`/`k`/`g`/`G`/`PageUp`/`PageDown` 移动的是**导入行**，不再是表单字段。
这是子模式而非叠加：面板正在展示"这个主机声明了哪些转发"，此时让方向键去改表单高亮，
用户按 `↓` 想看完剩下的行却看到表单滚走了。`tab` 仍然切表单字段，`ctrl+s` 仍然保存——
面板不能把整个表单吞掉。`esc`/`i` 收起面板后，字段导航立即恢复。

但这条"键位归面板"有一个必须写明的例外：**某个文本字段正在编辑时，键位归字段**。
面板从"按需打开"变成"默认就在"之后，这个例外从可选变成了必需——否则在名称里输入 `api-db`
会依次触发 `a`（全选）、`i`（收起面板），用户眼看着勾选被改掉、面板消失，而自己只是在打字。
守卫条件是 `is_editing_field()`，不是"面板开没开"：退出编辑（`enter`/`esc`）后，`j` 立刻
重新是行光标。判定放在 `handle_import_key` 之前，所以面板连"这个键我要不要"都不参与
编辑态的竞争。

### 全选只看筛选后的视图

`check_all_visible` / `uncheck_all_visible` / `invert_visible` 都只遍历 `visible()`。
这不是实现细节，是安全约束：带筛选时"全选"若勾上隐藏行，用户看到 3 行只勾了 1 行，
保存却创建 3 条隧道——起 3 个监听端口。同一条规则也保护了主表多选（§15）。

## 15. 多选模式与批量操作

单行流程每次问"删除**这一条**？"，扩展到"停这八条"就不合适了。多选模式让目标集合在
任何按键生效**之前**就明确可见。

`v` 进入/退出。进入时**不预标记**当前行——否则第一次 `space` 会**取消**用户刚指的那一行，
读起来像 bug。`space` 前后语义一致：切换光标行的标记。

| 键 | 作用 |
|---|---|
| `space` | 切换光标行标记 |
| `j`/`k` | 移动光标（标记保留） |
| `J`/`K` | 从锚点扩选到光标 |
| `a` | 全选可见行；再按一次全部取消 |
| `s`/`x`/`R`/`D` | 批量 启用 / 停用 / 重启 / 删除 |
| `esc` | 退出（清空标记） |

大写 `R`/`D` 用于批量重启用/删除，避免和单行的 `r`/`d` 混淆。

### 标记按 `TunnelId`，不按行号

过滤和删除都会让行移动。若标记存行号，一次删除后原来的"第 3 行"就指向另一条隧道，
**批量删除会删错东西**。`MultiSelect` 存 `BTreeSet<TunnelId>`：集合天然去重、天然保序
（提示文案和日志按同一顺序读），且删除后可用 `retain_existing` 清掉失效 id。

### 四种批量操作都过确认闸

包括"启用"——它一次开 N 个监听端口，和单行启用全部是同一类风险。提示用**有效条数**：
标记 3 条但只有 1 条在运行时，停用提示说 1 条。已经处于目标状态的条目不算进去，
否则用户确认的是一个比实际执行更大的数字，久了就会无脑按 `y`。

标记为空或全部无需变化时**不弹窗**，直接提示「没有选中任何条目」/「选中的 N 条都无需停用」。
让人确认"什么都不做"是噪音。

## 16. 鼠标：语义命中图

`src/ui/hit.rs` 的 `HitMap` 每帧重建，记录"屏幕这块矩形是什么意图"——不是矩形坐标本身：
点列头解析为 `ImportColumnHeader(col)`，而不是 `x=23`。

三条规则：

1. **只有渲染器写**，每帧开头 `clear()`。陈旧的图会把点击送到上一帧的布局。
2. **后 push 的赢**（`entries.iter().rev().find(...)`）。弹窗后画，自动遮蔽下面的表格，
   不需要任何 z-index 计算。
3. **零面积矩形被忽略**（`width == 0 || height == 0` 直接 return）。隐藏的控件不能截走点击。

第 2 条尤其值得强调：手工维护层级需要"谁盖谁"的全局知识，而绘制顺序本来就已经表达了它。
把层级从绘制顺序里**推导**出来，两者不可能不一致。

但"后画就能遮蔽"有个前提容易被忘掉：命中图是一个**栈**，不是 z-index。弹窗画在表格之后，
如果它**不记录自己的矩形**，表格的矩形仍然留在栈顶，点击就穿过弹窗落到表格行上——视觉上
弹窗盖住了表格，行为上却没有。所以 `draw_help` / `draw_confirm` / `draw_detail` 都会先把
自己的 popup 矩形记成 `HitTarget::Popup`（一个"吞掉点击、什么也不做"的目标），再画内容。
确认框尤其不能穿透：它是在破坏性动作**之前**拦人的，一次本想点对话框的点击绝不能落到某行上
把它标记或启动。

回归测试 `keys::tests::a_modal_swallows_clicks_instead_of_passing_them_to_the_table`
在弹窗背后放一个表格行，断言点击被消费、光标不动、也没有任何行被标记。

### 为什么不存坐标

渲染器已经算过布局。在事件处理里重新推导一遍就是**第二个真相来源**，它会漂移——改一个
列宽或加一行页脚，鼠标就点错位置，而键盘完全正常，于是 bug 很难发现。现在布局只有一处，
鼠标和键盘调用同一批 `App` 方法（`request_batch`、`import_toggle_at`…），所以鼠标**免费继承**
键盘的安全规则：点批量删除按钮一样要过确认框。

点击落空（没有命中任何 target）**什么都不做**，不"透传"给下面的控件。按钮旁边的误点
不该启动隧道。

### 鼠标能做什么

| 位置 | 动作 |
|---|---|
| 主表行 | 移动光标；多选模式下同时切换标记 |
| 主表行 + shift | 从锚点扩选范围 |
| 导入表复选框 | 切换该行勾选 |
| 导入表行其它位置 | 移动光标到该行 |
| 导入表列头 | 开始编辑该列筛选 |
| 筛选 chip `×` | 删除该列筛选 |
| `全选` / `反选` / `全不选` | 对应操作（只作用于筛选后可见行） |
| `清除全部筛选` / `撤销筛选` | 对应操作（无内容时变暗且**不可点**） |
| 多选动作条按钮 | 对应批量操作（走确认闸） |
| 列表上的滚轮 | 滚动（主表移动光标，导入表移动其光标） |

变暗的按钮**不记录 hit**，所以点击不会"看起来没反应"或误触相邻按钮。

鼠标捕获在 `main.rs` 里 best-effort 开启：终端拒绝捕获（某些 multiplexer、某些 CI pty）时
忽略失败，键盘 UI 仍然完整可用。退出前必定 `DisableMouseCapture`——留着它会让重新获得
控制权的 shell 每次鼠标移动都打印转义字符。

## 17. 诊断日志：一份能带走的证据

TUI 的详情面板已经有一份日志（`model::LogRing`），但它活在内存里、进程一退就没了、
且只覆盖单条隧道。这三个属性恰好都在**出问题之后**变成致命缺陷：

* 崩溃时没有界面可读；
* 用户要贴给我们的东西必须是**文件**，不是截图；
* "一小时前开始不对劲"需要跨隧道、跨事件的时间线。

所以另开一条独立的落盘通道（`src/logging.rs` + `app::log`）。两者不合并：面板要的是
"当下这条隧道发生了什么"，文件要的是"事后能不能还原现场"，对容量、留存、格式的要求不同。

### 格式：一行一条，列顺序固定

```
2026-11-08T18:55:42.957+08:00 INFO  seq=12 event=tunnel.ready tunnel=3 name=cloud-pc forward=local listen=127.0.0.1:19711 target=127.0.0.1:22 host=cloud_pc elapsed_ms=812
```

**不用 JSON。** 这个文件的读者是"拿着终端排障的人"和"`grep`/`awk`"，不是日志聚合器。
JSON 每行都重复键名，肉眼扫起来噪声占一半，而 `key=value` 用 `grep 'tunnel=3 '` 就能
切出时间线。真需要机器消费时，这个格式解析起来也只比 JSON 多一行 split。

**固定列顺序**（时间、级别、seq、event）让 `cut`/`awk '{print $2}'` 有意义；
**隧道身份 6 字段固定在前**让任何一条隧道级记录都能脱离上下文被读懂。

**值必须转义。** 记录里塞进一个裸换行会把一条日志劈成两条，后面所有按行处理全部错位。
所以含空白/引号/反斜杠/控制字符的值一律加引号并转义（`\n` `\r` `\t` `\\` `\"` `\xNN`），
键名与事件名则把这类字符替换成 `_`。有测试钉住"一条记录不跨行"。

### 级别：按"读的人要做什么"划分，不是按"严重程度"

* `ERROR` — 用户要做的事没做成，或隧道已死且不会自愈。
* `WARN` — 降级但自愈：安排了重连、学到新主机密钥、配置被修正、一帧超时。
* `INFO` — 预期内的生命周期，足以在不看 UI 的情况下重建一次会话。
* `DEBUG` — 高频细节（每条转发行、每次 SOCKS5 失败、状态机每一步）。

关键判断：**掉线（`was_up=true`）是 WARN，从未连上的失败是 ERROR。** 前者是网络抖了一下、
系统会自己重连；后者要用户动手。同理 `tunnel.failed` 带 `retryable` 字段——读者不用去猜
"这个错等一下会不会自己好"。

`SSHPF_LOG_LEVEL=off` 只关常规记录，崩溃记录无条件写。想把日志关掉的人，往往正是最需要
那一行崩溃信息的人。

### 崩溃捕获：两条独立通路

**panic** 走 `set_panic_hook`，链式调用上一个 hook（所以 `ratatui` 恢复终端的逻辑照常生效），
写 `crash.panic` + `crash.panic.trace` 两条记录。`thread` 字段是关键：每条隧道跑在自己的
线程上（`sshpf-tunnel-<id>`），线程名能区分"UI 崩了"和"某条隧道的线程崩了"——后者在
`tunnel.status` 上看起来只是"没连上"，没有这条记录根本查不出来。

栈只保留前 25 帧：debug 构建的栈顶 30 帧几乎全是 `std::panicking` 的管道代码。

**致命信号**（SIGSEGV/SIGBUS/SIGABRT/SIGILL/SIGFPE）走 `sigaction`。这里有一条硬约束：
处理器里只能用 async-signal-safe 调用——不能分配、不能加锁、不能用格式化机制。所以它：

1. 若 TUI 正在持有终端，先写转义序列退出备用屏（否则用户卡在残留画面里，光标都看不见）；
2. `write(2)` 一条**手工拼好**的记录到预先 `dup` 出来的 fd，整数逐位自己转十进制；
3. 往 stderr 写一行预置的提示（启动时就拼好，处理器里不做格式化）；
4. 恢复默认处理器 → **解除内核对该信号的屏蔽** → `raise`。

第 4 步的解除屏蔽容易漏：内核在处理器执行期间屏蔽该信号，不解除的话 `raise` 只是把它排队，
随后 `_exit(139)` 抢先执行，进程就从"被 SIGSEGV 杀死"变成"以 139 退出"，**core dump 也不会
产生**。这是实测发现的（`a_fatal_signal_keeps_the_signal_exit_status` 钉住它）。

代价是这一条记录**没有格式化时间戳**，只有 `ts=<epoch 秒>`（`localtime_r` 首次调用会分配内存）。
其余字段仍是 `key=value`，解析器不需要为它开特例。宁可时间戳不漂亮，也不要在这个位置引入
一次可能再崩一次的内存分配。

递归崩溃由 `SA_RESETHAND` 兜住：第二次触发走默认动作，不会死循环。

### 隐私与权限

记主机名、端口、用户名、失败原因、路径、版本、pid、栈；**不记**私钥内容、passphrase、
`known_hosts` 内容。文件 `0600`、目录 `0700`，与配置同级——日志里出现了主机名和用户名，
就不能比配置文件更宽松。

### 轮转：先轮转，再写

单文件 2 MiB 触发轮转，保留 3 个归档（`.1` 最新）。顺序是先轮转再追加，所以一条记录
**永远不会跨两个文件**——跨文件的半条记录是不可解析的，而轮转边界正好是崩溃排查最可能
落到的位置。归档重命名失败一律忽略：丢历史好过丢当下。

### 日志永远不许把程序搞挂

打不开文件 ⇒ logger 降级为 disabled，所有写入变成空操作；写入失败 ⇒ 吞掉（没有地方上报，
重试只会死循环）。`init` 的失败原因会留在 `init_error()` 里，TUI 起来后写进状态栏
（"日志未启用: …"）——静默失败是这个可观测性功能最糟的失败模式：用户以为有日志，
出事时打开只有空文件。

### 高频路径不写

每条转发连接成功与否都要过日志的话，`-D` 代理几秒钟就能刷满文件。所以
`tunnel.line` / `socks5.rejected` / `forward.target_failed` 之类的线程侧事件只在
`DEBUG` 级别写，并且**先查级别再拼字符串**（`enabled()` 短路），避免为了丢弃而格式化。

### UI 卡顿也记

事件循环每帧量一次耗时，超过 500 ms（tick 的 2.5 倍）记一条 `ui.slow_frame`。
"TUI 感觉卡住了"是最难复现的一类反馈，一行带毫秒数的时间戳能立刻区分
"某一帧卡了"和"整个事件循环卡死"。

## 18. 界面帮助体系：把"不得遗漏"变成可执行断言

需求原文是「**所有操作、所有按键操作**，都要在界面上提供明确按键说明，**不得遗漏**」。
"不得遗漏"是一个全称命题，而全称命题无法靠人工检查守住：每次加一个键、改一次模式重绑，
就有一次遗漏的机会，而遗漏的表现是**静默的**——用户不知道有个键存在，因此永远不会报 bug。

所以这里不做"补一份更全的文档"，而是把它变成一条会变红的测试。

### 帮助是数据，不是散文

`src/help.rs` 没有任何渲染代码，只有数据：

```rust
pub const SECTIONS: &[HelpSection] = &[
    HelpSection {
        id: SectionId::Main,
        title_zh: "主界面", title_en: "Main screen",
        items: &[
            HelpItem::new("j / ↓", "向下移动光标", "Move the cursor down"),
            HelpItem::new("k / ↑", "向上移动光标", "Move the cursor up"),
            // …
            HelpItem::note("没有未启用条目时 a 只给提示，不弹确认框。",
                           "With nothing off, a only reports it."),
        ],
    },
    // … 14 个上下文各一节
];
```

四个理由，按重要性排序：

1. **可测试**。数据能被另一段程序读，散文不能。这是整节存在的理由。
2. **可计数**。`item_count()` 是浮层滚动上限的输入之一；帮助是散文时，滚动条只能靠猜。
3. **双语同源**。中英并排写在同一个 `HelpItem` 里，而不是两份文档——两份文档必然漂移，
   而且漂移总是发生在没人看的那一份上。
4. **一处措辞**。浮层与界面底部提示行复用同一批文字，所以"页脚说的"和"`?` 说的"不可能
   互相矛盾。页脚写 `space 勾选`、帮助写 `space 启停`，是比缺失更糟的**错误信息**。

`keys` 的书写规范（团队契约 §3）也被固定下来：并列键用 `" / "` 分隔、修饰键用 `+` 粘住、
方向键写成 `↓ ↑ ← →`。这些规范不是为了好看，而是为了让测试能**无歧义地切分**——
切错一个 token，"覆盖"就变成了假的。

### 覆盖测试：两个方向都要断言

`tests/help_coverage.rs` 在编译期用 `include_str!` 同时嵌入 `src/keys.rs` 与 `src/help.rs`，
从前者**解析**出真相，与后者比对。两个方向都要查，因为它们是两种不同的缺陷：

| 方向 | 断言 | 漏了会怎样 |
|---|---|---|
| 正向 | 代码 dispatch 的每个键，帮助里必须有 | 用户的键做了事，帮助里却没有说明（**不得遗漏**） |
| 反向 | 帮助写的每个键，代码里必须真的 dispatch | 用户按下去什么都不发生，然后不再相信帮助（**不得撒谎**） |

反向断言看着多余，其实是最容易踩的坑：删掉一个键的 dispatch 而忘了删帮助行，非常常见，
而它的后果比缺失更严重——缺失只是信息不全，撒谎会摧毁整份帮助的可信度。

固化这两条只需一次，收益是之后每加一个键都被自动检查。

#### 解析：花括号配平，不靠缩进也不靠行号

handler 体这样取：先按 `fn <name>(` 找到签名，然后从函数体第一个 `{` 开始做**花括号配平**，
走到深度归零的那个 `}`。不用缩进（`rustfmt` 会改）、不用行号（改一行就全错位）、
不用正则匹配整个函数（Rust 的嵌套块让正则不可靠）。

扫描前先把**注释和字符串字面量**涂成空格，但保留字符字面量：

- 注释必须涂掉，因为这份 dispatch 代码注释极多（"`f` 在筛选输入之上"、"`i` 收起面板"），
  不涂就会把散文里提到的 `KeyCode` 或 `KeyModifiers::CONTROL` 当成真的 dispatch；
- 涂成空格而不是删除，是为了让偏移量与原文对齐，报错时能指回原文件；
- 字符字面量要保留，因为 `Char('j')` 的 `'j'` **就是**要抽的载荷。

`KeyCode::Char(c)`（变量模式）不产生 token：它表示"任意字符"，无法枚举。给伪造一个 token
会让比对失去意义。需要表达"直接输入即过滤"的 section，用 `HelpItem::note` 写——note 没有
`keys`，天然不参与覆盖检查，这正是 note 的用途。

修饰键的作用域是**单个 match arm**（从每个字面量向两侧扫到最近的 `=>` / `;` / `{` / `}`），
不是整行、也不是整个函数体：同一函数里相邻 arm 的 `SHIFT` 守卫不能串味，多行 arm 也要能
正确归因。

#### 白名单要写成常量并注明理由

零例外是理想，但真实代码里有几处**刻意**的跨 section 引用。它们必须显式、有名字、有注释：

```rust
/// * `("import_pane", "ctrl+s")` — handle_import_key 对它 return false，故意交回表单，
///   这样面板开着也能保存。dispatch 在 handle_field_navigating，但用户在面板页脚读到它。
const DOC_ONLY: &[(&str, &str)] = &[("import_pane", "ctrl+s")];

const CODE_ONLY: &[(&str, &str)] = &[];   // 对称的另一半，目前为空
```

用"忽略失败"或注释掉断言来掩盖差异，等于把测试变成仪式；写成常量加理由，则是把例外变成
**设计决策**——下一个人看到它就知道这是有意为之，而不是需要修掉的漏洞。

#### 符号归一化

两边拼写习惯不同：代码里是 `KeyCode::Down`，界面上用户看到的是 `↓`；终端把 Shift+J 报成
大写 `'J'`，而源码里同一个绑定可能写成 `Char('j')` + `SHIFT` 守卫。所以比对前统一归一化：
`↓↑←→` → `down/up/left/right`，`shift+<字母>` → 大写字母。

这里有个真实教训：反向断言最初报 `form_editing` 多出 `ctrl+s` / `f10`。查下去发现**不是**
帮助写错，而是编辑态真的没有 dispatch 这两个键——保存只在导航态有效，于是用户在编辑一个
字段时按 `ctrl+s` 什么都不发生，而页脚一直写着"`ctrl+s` 保存"。更糟的是 `Char(c)` 会先命中
`edit_field`，把 `s` 当普通字符**打进字段**：不是快捷键失灵，是静默的数据损坏。

测试抓到这个缺陷后，`keys.rs` 里补上了与阶段无关的保存分支，两个方向随即同时变绿。
这正是这套测试的价值：它发现的不是"文档少了一行"，而是"文档和代码里有一处真的错了"。

#### 帮助浮层按折行后的行数滚动

帮助一旦分区、每条同时给中英文，条目数就不再等于屏幕行数：窄终端上一行会折成两三行。
所以 `clamp_scrolls` 的滚动上限必须按"当前宽度下折行后的实际行数"算，而且渲染与限位
必须调用**同一个**纯函数——`ui::help_lines(width, palette) -> Vec<Line>`，它把
`SECTIONS` 编排成行：分区标题 `中文 · English`（加粗 + 下划线 + accent），条目行
`键列 | 中文 | 英文`，note 行整行 prose。键列宽度是**实测**的：取目录里最宽的那个
binding 再 +2，钳制在 `[10, 22]` 且不超过半行（`help_key_col`）。写死过 12，结果是
`g / G / home / end`（18）和 `J / K / shift+↓ / shift+↑`（25）直接贴住说明——
`pad_to_width` 只补不截，于是渲染成 `g / G / home / end跳到首行`。少数超长 binding
会单独占一行，说明从下一行按键列缩进开始；双语放不下时中文先排、英文换到续行。
渲染与滚动上限共用一个函数，两者不可能不一致。
否则要么滚到底留白，要么提前卡住——用户会以为帮助被截断了。

#### "中文在前、英文在后"的兼容性理由

双语化的最小破坏形式是 `中文 English`（`help::bi`）。除了阅读顺序，还有一条工程理由：
仓库里大量既有断言是 `contains("中文")`，中文在前能让它们继续通过。这不是妥协，而是
把"双语化"做成**增量**——文案改动不该顺带改掉测试的判据。

窄宽度下用 `fit(zh, en, width)` 三级退化：双语 → 只中文 → 截断。**不做**半个英文短语：
一个被截断的英文句子比没有更糟，用户会以为那是完整信息。

#### 人工文档也在检查范围内

`docs/keymap.md` 是 `?` 装不下的完整参考（`?` 是摘要，keymap 是手册）。它同样会落后，
所以测试也断言：帮助目录里出现的**每一个 token** 都必须在 keymap 里有据可查。
三层（代码 → 帮助 → 手册）任一层漂移都会让测试失败：

```
src/keys.rs ──解析──▶ 代码 token ──┐
                                  ├─ 必须相等（双向）
src/help.rs ──切分──▶ 帮助 token ──┘
         │
         └──▶ 每个 token 必须出现在 docs/keymap.md
```

`src/ui/hit.rs` 的 `HitTarget` 走同一条路：测试解析枚举变体名，断言每个变体都在
`SectionId::Mouse` 里被说明。鼠标是最容易漏的那一类——它不在 `keys.rs` 里，加一个可点
控件（比如新的 footer 按钮）不会有任何键位变化来提醒你补文档。枚举变体清单把这个漏洞
也堵上了：新增 `HitTarget` 变体却不写帮助，测试直接失败。

## 19. 防御式边界

这个程序读的东西全都不由我们控制：`~/.ssh/config` 是用户（或 dotfiles 管理器、或某个
脚本）写的文本，`config.toml` 允许手改，环境变量是 shell 里的字符串，`stdin`/`stdout`
可能根本不是终端。所以有一条硬边界：

> **边界之外是任意的，边界之内不许 panic；出问题就降级，降级必须留痕。**

分三层，从外到内：

**第一层：输入解析一律不 panic。** 解析器面对的是"字节"而不是"我们已经相信的字符串"。
这一轮真正崩过的两处说明了违反它是什么后果：

- `strip_match_blocks` 用 `trimmed[..5]` 比较 `Match` 关键字。首行是中文注释时，第 5 个
  字节落在一个 3 字节字符中间 ⇒ `byte index 5 is not a char boundary`。修法是按**字节**
  比较（`as_bytes().get(..5)`），这本来也是 OpenSSH 的关键字语义：ASCII 大小写不敏感。
- `std::env::args()` 对每个参数 `unwrap()` 成 UTF-8。路径是 `OsStr`，不是 `String`；
  非 UTF-8 的路径在非 UTF-8 locale 下完全合法。改用 `args_os()`，路径按字节原样保留，
  作**参数名**时才拒绝（那时它确实无法匹配任何已知 flag）。

同类替换贯穿全部边界：`print!`/`println!`（写失败即 panic）改成显式句柄上的 `write_all`；
`ratatui::init()`（内部 `expect`）改 `try_init()` 并把 `io::Error` 交给正常的 `app.fatal` 通路；
所有 u16 算术先扩宽到 u32、用 `try_from` 收口；`max_id() + 1` 改 `saturating_add`。

**第二层：只剩不变量可依赖的地方，降级而不是断言。** 有些下标"逻辑上一定安全"，但这个
"一定"依赖于 ratatui 的 layout 契约、或某个 `len()` 与常量保持同步——两者都可能在下一次
依赖升级或一次重构里悄悄失效，而代价是整帧 panic（终端停在 raw mode，界面全无）。
这类位置改成 `get()` + 安全默认值：

- 渲染层拿不到该有的 layout 分区 ⇒ 这一块这一帧不画，记 `ui.render_degraded`
  （`reason=layout_band_missing`）。
- 表格行号 + 表头顶出 `u16` ⇒ 视为"在屏幕外"，不再进命中图。
- `ForwardKind::all()[kind_idx]` 越界 ⇒ 回落默认类型，记 `form.kind_index_invalid`。
- 确认框的目标隧道已被删 ⇒ 对话框照常开（不卡住用户），渲染时没有名字，记
  `action.target_missing`。

代价是"降级"很容易变成静默的。所以有一条附加规则：**每次降级都写一条记录，
且渲染层这类每帧都可能触发的路径必须限流**（`ui.render_degraded` 每进程每处只记一次，
否则一次 resize 就能把 2 MiB 的日志刷满、把真正有意思的历史挤掉）。

**第三层：日志系统自身是最后防线。** 前两层保证"别的地方不 panic"，但崩溃捕获机制本身
也可能挂，而它挂了就什么都没了。三个约束：

1. **panic hook 必须自安全。** 它要写日志，而写日志要拿锁。如果 panic 恰好发生在持锁的
   写入过程中（某个值的 `Display` 里 panic 就会这样），hook 的 `lock()` 就是自己等自己
   ⇒ 进程永久僵住。注意这**不是** `Mutex` 的 poison 语义：同线程重入不会返回
   `Err(poisoned)`，而是直接挂死，所以"中毒了 `into_inner()` 一下"那种处理救不了它，
   必须事先识别出"我就在临界区里"。用的是一个 thread-local 的
   `Cell<bool>` 哨兵（`CriticalSection::enter()`，RAII `Drop` 复位，panic 展开也会复位）：
   已在本线程的临界区内就直接降级、不碰锁，改用启动时 `dup` 出来的 fd 裸 `write(2)`
   写一行 `crash.log_reentrant`（`ts=` epoch 秒、不分配、不格式化，和 `crash.signal`
   同一风格），然后让原 panic 照常传播。**宁可少一条记录，不能不死。**
2. **信号处理器只做 async-signal-safe 调用。** 不分配、不加锁、不用格式化机制；
   记录是手工拼进固定缓冲区的，整数逐位转十进制，时间戳用 `time(2)` 而不是
   `localtime_r`（首次调用会分配内存）。
3. **线程 panic 不传染进程。** 每条隧道在自己的线程上，`catch_unwind` 把 panic 转成
   `Event::Exited{code:101}` + `tunnel.thread_panic`；该行变成失败态，UI 和其余隧道继续。

这一层只保"记录得下来"，不保"程序活着"——进程该崩还是崩，退出码和 core dump 行为不变
（`a_fatal_signal_keeps_the_signal_exit_status` 钉住这一点）。把崩溃静默掉才是更坏的选择：
用户会拿到一个行为异常但不报错的程序。
